# ampdent_data

Offline-first local store for AmpDent: Drift/SQLite tables for every
`ampdent_core` entity, abstract repositories with Drift implementations, an
append-only audit log, a sync outbox and first-open seeding, plus the
Supabase sync engine that drains the outbox and pulls server changes
(see "Sync"). The only network code is PostgREST through `package:supabase`.

```dart
final db = AppDatabase.open('ampdent');          // device
final db = AppDatabase.inMemory();               // tests
final repos = DriftRepositories(db);
const ctx = ActorContext(clinicId: ..., actorId: ..., deviceId: ...);
await repos.patients.upsert(ctx, patient);       // audited + queued for sync
```

## Code generation

`lib/src/db/app_database.g.dart` is generated by `drift_dev` and gitignored.
Regenerate it after any table change:

```bash
dart run melos run gen            # repo root
# or
cd packages/data && dart run build_runner build --delete-conflicting-outputs
```

## Storage conventions

| Dart type | SQLite | Notes |
|---|---|---|
| `Money` | INTEGER | paise (`MoneyConverter`) |
| `ToothId` | TEXT | FDI `storageKey` (`36`, `55+1`) |
| `List<ToothId>` | TEXT | JSON array of storage keys |
| `SurfaceSet` | TEXT | canonical code (`MOD`), empty string for none |
| enums | TEXT | `.name` via `textEnum` |
| `DateTime` | TEXT | ISO-8601 **UTC, millisecond precision** (`2026-10-18T09:30:00.000Z`) |
| `num` | REAL | `NumConverter` keeps the Dart type `num` |
| lists / maps of value objects | TEXT | JSON through the entity's own `toJson`/`fromJson` |

Dates: every `DateTime` is normalised to UTC on write (`encodeIsoUtc`) and
comes back as a UTC `DateTime`. The fixed format makes lexicographic order
equal chronological order, so range queries compare the stored strings
directly (`t.startsAt.isBiggerOrEqualValue(encodeIsoUtc(from))`).

Tables map onto the core entities with `@UseRowClass(..., generateInsertable:
true)`: there is no second data class to keep in sync, and `entity
.toInsertable()` writes a row. `generateInsertable` is deprecated upstream in
favour of `write_to_columns_mixins`, which would require mixing a generated
mixin into the core entities; since `ampdent_core` must stay codegen-free,
the deprecated flag is the right tool and the deprecation lint is suppressed
per table file. `treatment_plan_lines` carries a data-layer `removedAt`
column the entity does not have, so its companion is hand-written.

Every tenant table has `clinic_id TEXT NOT NULL REFERENCES clinics(id)`, an
index on `(clinic_id)` and the obvious secondary indexes; patient-scoped
tables also reference `patients(id)`. Foreign keys are enabled in
`beforeOpen`.

## Append-only writes

Every repository is a `DatabaseAccessor` with the `AuditedWriter` mixin.
Each write runs in one transaction that also appends:

* an `AuditEvent` (actor, device, action, entity type/id, before/after JSON;
  `occurredAt` is the device clock at write time, never the business time),
* a `sync_outbox` row with the row JSON after the write (`insert`/`update`;
  there is no `delete` operation).

Nothing hard-deletes. "Delete" methods move rows to a `deleted` status or
`isActive = false` and audit with `softDelete`; plan lines dropped from an
unaccepted plan get `removedAt`; signed notes are superseded by a new version;
perio exams, medical histories, payments, ledger entries, consents,
prescriptions, tooth states and sterilisation cycles refuse re-writes.
`test/audit_export_test.dart` greps the sources to prove no drift delete API
is called.

Append-only tables are listed in `appendOnlyTables` (`audited_writer.dart`).
`audited()` calls `ensureAbsent(table, id)` before a create on one of them and
throws `StateError` when the id already exists, so an upsert path can never
silently overwrite a signed consent or a payment; repositories may also call
`ensureAbsent` directly for a clearer message. Perio site readings are plain
inserts (no `insertOrReplace`): a re-examination is a new exam id.

Recalls created from completed procedures are idempotent per triggering
procedure, and a new recall dismisses any older open recall of the same type
for the patient (audit reason `superseded by recall <id>`), so the overdue
KPI and reminders count each patient once per recall type.

Ledger postings are written in the same transaction as the invoice issue,
payment or adjustment they mirror.

## Errors

`writeTransaction` rethrows SQLite failures as `RepositoryException`, which
carries the extended result code (`SQLITE_CONSTRAINT_UNIQUE`, ...), the table
and the violated constraint's column identifiers, and nothing else. The raw
`SqliteException` is dropped because its `toString()` prints the statement's
bound parameters, i.e. the patient row. Log `RepositoryException` freely;
never catch and log the drift/sqlite exception underneath it. Application
errors (`StateError`, `ArgumentError`) pass through unchanged.

## Numbering

Identifiers minted offline must survive the server's unique indexes
(`patients (clinic_id, patient_number)`, `invoices (clinic_id, number)`,
`estimates (clinic_id, number)`) when several phones of one clinic sync.

* Every device has a four-character **device code**: the first four
  alphanumerics of its device id, upper-cased (`SettingsAccess.deviceCode`;
  device ids are UUID v4, so these are hex digits).
* **Draft documents**: `DRAFT-INV-yyyyMM-<code>-0001`,
  `DRAFT-EST-yyyyMM-<code>-0001`, from the per-device counters
  `counter.draftInvoice.<code>` / `counter.draftEstimate.<code>`
  (`SettingsAccess.mintLocalDraftNumber`). The server replaces the whole
  string when it mints the real number.
* **Patient numbers**: the clinic has one **primary device**
  (`SettingKeys.primaryDeviceId` = `device.primary`, seeded with the device
  that created the clinic, movable with `ClinicRepository.setPrimaryDevice`).
  Only the primary mints plain `P-00001` from `counter.patientNumber`; every
  other device mints `P-<code>-00001` from `counter.patientNumber.<code>`.
  A clinic with no recorded primary (created before the setting existed) is
  claimed by the first device that mints a number.
* Sterilisation cycle numbers (`SC-00001`) stay per clinic: they are not
  unique server-side.

## Encryption at rest

The SQLite file is **not encrypted yet**; it relies on the OS app sandbox and
the device lock. Decision: SQLCipher through drift's encrypted
`NativeDatabase` (`sqlcipher_flutter_libs`, `PRAGMA key` in the `setup`
callback, key in the platform keystore); the sync engine works on Drift rows
and is unaffected by the storage layer. The `TODO(security)` sits on
`AppDatabase.open`.

## Seeding

`beforeOpen` seeds the global procedure catalogue (`indianProcedureCatalogue`,
`clinic_id` NULL) and the drug master (`dentalDrugMaster`) when empty, with
deterministic UUID v5 ids so every device agrees. `ClinicRepository
.createClinic` seeds the clinic's GST rate history, display notation and
numbering counters into `settings`. No demo data.

## Sync

`SyncEngine` is the contract (`state`, `pushPending`, `pullSince`).
`NoopSyncEngine` serves tests and local-only installs; `SupabaseSyncEngine`
replicates one clinic with a Supabase project over PostgREST. Realtime is not
used. Everything lives in `lib/src/sync/`:

| File | Role |
|---|---|
| `supabase_sync_engine.dart` | `SyncEngine` over a `SupabaseClient`: state stream, mutex, token/link checks |
| `sync_pusher.dart` | `OutboxPusher`: drains `sync_outbox` as PostgREST upserts in FK order |
| `sync_puller.dart` | `TablePuller`: keyset-paged pull per table, conflict policy |
| `sync_tables.dart` | the ordered table list, per-table policy, push plan with fix-up steps |
| `row_codec.dart` | `SyncRowCodec`: Drift row <-> server JSON from table metadata |
| `sync_state_repository.dart` | `sync_state` table: watermarks, device id, clinic link, last sync |
| `sync_scheduler.dart` | `SyncScheduler`: on demand, debounced after writes, interval, app hooks |
| `remote_clinic_linker.dart` | `RemoteClinicLinker`: first-device push / second-device adopt |
| `sync_errors.dart` | `SyncFailure`, `classifySyncError`, `inferHttpStatus`, `BackoffPolicy` |
| `sync_repair_service.dart` | `SyncRepairService`: list, retry and discard quarantined rows (`SyncProblem`) |
| `device_heartbeat.dart` | `DeviceInfo` value object and `DeviceHeartbeat`: the `devices` row, once per 15 minutes |
| `reachability.dart` | `Reachability`: `HEAD`/`GET` probe of `<SUPABASE_URL>/auth/v1/health` |

### Wiring (the app owns sign-in)

```dart
final client = SupabaseClient(
  supabaseUrl, supabaseAnonKey,
  accessToken: () async => session?.accessToken, // or let supabase_flutter manage auth
);
final engine = SupabaseSyncEngine(
  client: client,
  db: db,
  clinicId: clinicId,
  accessTokenProvider: () async => session?.accessToken,
  deviceInfo: const DeviceInfo(
    appVersion: '1.2.0+45',
    platform: DevicePlatform.android,
  ),
);
await engine.restoreLastSyncTimes();
final scheduler = SyncScheduler(
  engine: engine,
  pendingCount: repos.outbox.watchPendingCount(clinicId),
  accessTokenProvider: () async => session?.accessToken,
  reachability: Reachability(supabaseUrl: Uri.parse(supabaseUrl)),
)..start();
// app hooks: scheduler.onConnectivityChanged(online: ...), scheduler.onAppResumed(),
// scheduler.probeReachability() (on resume and on a timer),
// scheduler.syncNow(), scheduler.pause() / resume()
// repair: engine.repair.listProblems() / retry(id) / discardLocalChange(id, ctx)
```

The engine only calls `client.from(...)`; it never signs in or touches
`client.auth`. While `accessTokenProvider` returns null the engine reports
`SyncStatus.offline` with error `signed out` and does nothing; the scheduler
skips its automatic runs too.

### Push

1. Pending outbox rows (`acked_at IS NULL`) are grouped by table and row id;
   repeated writes of one row collapse into a single upsert of the row's
   **current** local state (read from the table, not from the outbox payload).
2. Tables are visited in `syncTables` order, which follows the server foreign
   keys: `clinics`, `clinic_members`, `chairs`, `settings`, `catalog_items`,
   `drugs`, `labs`, `patients`, `appointments`, `visits`, ... children last,
   `audit_events` at the end. Two FK cycles (`treatment_plan_lines.procedure_id`
   -> `procedures`, `procedures.lab_case_id` -> `lab_cases`) are broken by
   leaving the referencing column out of the main upsert and writing it in a
   fix-up step (`id` + that column) once both sides exist.
3. Each table is sent in batches of 200 as `POST /rest/v1/<table>` with
   `on_conflict=id` (`clinic_id,setting_key` for `settings`),
   `Prefer: resolution=merge-duplicates,missing=default`. Tables the server
   has no UPDATE policy for (`payments`, `ledger_entries`, `consent_records`,
   `prescriptions`, `medical_histories`, `tooth_state_records`) use
   `resolution=ignore-duplicates`, so a replayed row is a no-op instead of a
   policy violation.
4. `updated_at` is never sent: the server assigns it (default on insert,
   `app.touch_updated_at()` on update), so a write that was offline for a
   week still lands above every other device's watermark.
5. Outbox rows are acknowledged only after a 2xx for every step touching
   their table. A 5xx, 408, 429 or network error is retried with exponential
   backoff (`BackoffPolicy`: 1 s, 2 s, 4 s, ... capped, four attempts by
   default) and each attempt increments the rows' `attempts` counter and
   stores the error class in `last_error`; the push then stops with
   `SyncStatus.offline`. A 401 (or a `PGRST30x` JWT code) stops the push at
   once with `SyncStatus.offline` and "sign in again": the session, not the
   payload, needs fixing. Any other 4xx or Postgres error code (constraint,
   RLS) is permanent and **quarantines** the row instead of stopping the
   push (next section). Platform-wide `catalog_items`/`drugs` rows
   (`clinic_id` null) are acknowledged without being sent; they ship in the
   app.
6. `message_logs.provider` is omitted from the payload while null locally
   (rows from before schema v6) so the server default and its before-write
   trigger apply (`SyncTable.serverDefaultColumns`); `opt_in_reason` is a
   server column since migration 0011 and travels with the row. No synced
   table keeps a local-only column today (`SyncTable.localOnlyColumns` stays
   for the next one; the column parity test skips whatever it lists).
7. After a successful push the **device heartbeat** runs when
   `SupabaseSyncEngine(deviceInfo: DeviceInfo(appVersion:, platform:))` was
   given: one upsert of `devices` (`id` = the sync-state device id,
   `clinic_id`, `platform`, `app_version`, `last_seen_at` = the device clock)
   at most once per `heartbeatInterval` (15 minutes), with the last time kept
   in `sync_state` (`last_heartbeat_at`) so a restart does not repeat it. A
   heartbeat failure is logged and never fails the push.

### Quarantine and repair

A push used to stop at the first permanently rejected row and retry it on
every run, which left every later table unsynced. Now an unacknowledged
outbox entry carries a `status` (`OutboxStatus`, schema v6): `pending`,
`quarantined`, `blockedBy` or `discarded`; only `pending` rows are pushed,
`SyncState.pendingCount` counts those, and `SyncState.quarantinedCount`
counts the held ones (`quarantined` + `blockedBy`).

When a batch fails with a permanent error (`SyncFailure.isPermanent`: 4xx
other than 401/408/429, or a Postgres code such as `23503`, `23505`,
`42501`), the pusher re-sends the batch row by row to find the poison rows
(PostgREST upserts are one statement, so the server names no row), then for
each of them:

* every unacknowledged entry of that (table, row id) becomes `quarantined`,
  with `last_error` = error class plus the server's message (never its
  `details`, which can quote the row), `server_status_code` = the HTTP
  status (inferred from the Postgres code class when PostgREST hid it:
  `23xxx` -> 409, `42501` -> 403, `22xxx` -> 400; `inferHttpStatus`) and one
  more attempt;
* every `pending` entry whose local row references the quarantined row
  through a foreign key (read from SQLite's own `PRAGMA foreign_key_list`,
  so `clinic_id` -> `clinics`, `patient_id` -> `patients`) becomes
  `blockedBy` the quarantined entry's id, transitively, so a child is never
  sent ahead of a parent the server does not hold;
* the rest of the batch, the table and every later table carry on; the push
  ends `idle`, the report carries `rowsQuarantined` / `entriesBlocked`, and
  the held rows are not touched by later pushes.

A held row still protects the local copy on pull (local-pending-wins), and a
**new local write** of a quarantined row goes out as a normal `pending`
entry: if the server accepts it the older held entries of that row are
acknowledged (`ackHeldRows`), the entries blocked behind them go back to
`pending` (`releaseBlocked`) and the same push sends them in its next pass.

`SyncRepairService` (`engine.repair`) is the UI's handle:

* `listProblems()`: one `SyncProblem` per held row, oldest change first:
  table, entity type and a short label (patient name, invoice number,
  appointment start; never clinical text), status, error, status code, when
  the change was made, the blocking parent; `description` is one safe line.
* `retry(id)`: puts the row's entries and everything blocked behind them
  back to `pending`; the next push sends the rows' current local state.
* `discardLocalChange(id, ctx)`: marks the chain `discarded` (acknowledged,
  never sent) and makes each affected local row match the server: a
  last-writer-wins row the server holds is overwritten with the server copy
  (no audit event, no outbox row, like a pull); a row the server does not
  hold, or an append-only row, cannot be replaced (nothing is ever deleted
  locally), so it is noted in `sync_state` as `rejected.<table>.<row id>`
  (JSON: error, status code, outbox id, time; `rejectedRows()`,
  `clearRejected`) and an `AuditEvent` (`statusChange`, reason "sync: local
  change rejected by the server ...") is appended on the entity so the audit
  log keeps it visible.

### Reachability

`Reachability(supabaseUrl:)` is a pure-Dart probe: `HEAD
<SUPABASE_URL>/auth/v1/health` with a 3 s timeout (`GET` when the server
answers 405/404/501 to `HEAD`); any response below 500 means reachable, a
timeout, socket error or 5xx means not. `SyncScheduler(reachability: ...)
.probeReachability()` runs it and feeds the answer to
`onConnectivityChanged`, so coming back online triggers one run and an
unreachable server pauses the automatic ones; the app calls it on resume and
on a timer. Without a configured probe the run is the probe: an engine that
last reported `offline` is given one run.

### Pull

Per table, in the same order, `GET /rest/v1/<table>?clinic_id=eq.<id>`
(`id=eq.<id>` for `clinics`) with `order=updated_at.asc,id.asc&limit=1000`
and a keyset filter above the stored watermark
(`or=(updated_at.gt."W",and(updated_at.eq."W",id.gt."K"))`). The watermark is
the server's `updated_at` text verbatim (microseconds) plus the last row's
key, advanced after every page, so an interrupted pull resumes where it
stopped and a row updated mid-pull is simply fetched again (0008 gives every
table, `audit_events` included, a server-assigned `updated_at` and an index on
`(clinic_id, updated_at)`). A table with no watermark is pulled in full; `SyncStateKeys.lastFullSyncAt` records the end
of a pull that started with none. `pullSince(DateTime)` lowers every
watermark to that instant first; `resetWatermarks()` forces a full re-pull.

Pulled rows are written straight into the tables (no audit event, no outbox
row) inside one transaction per page, under the per-table policy:

| Tables | Policy | On pull when the row exists locally |
|---|---|---|
| `tooth_state_records`, `medical_histories`, `perio_exams`, `prescriptions`, `consent_records`, `payments`, `ledger_entries`, `sterilisation_cycles`, `audit_events` | **append-only** | kept; the server row is inserted only when absent. These are the tables the server itself refuses to UPDATE (0006), plus perio exams (snapshots; the puller rebuilds `perio_site_readings` for every inserted exam) |
| `procedures`, `findings`, `clinical_notes`, `data_consents`, `image_records`, `implant_records`, `adjustments`, `patients`, `appointments`, `visits`, `treatment_plans`, `treatment_plan_lines`, `estimates`, `invoices`, `recalls`, `lab_cases`, `licences`, `clinics`, `clinic_members`, `chairs`, `settings`, `catalog_items`, `drugs`, `labs`, `message_logs` | **last writer wins** | kept while the row has a pending outbox entry (local pending wins until pushed); otherwise overwritten when the server `updated_at` is later than the local one (always, for tables without a local `updated_at` such as `chairs`) |

"Append-only" in the domain rules means rows are never deleted, not that
they never change: procedures, findings, notes, DPDP consents, images,
implants and adjustments carry status transitions (completed, deleted with a
reason, withdrawn, signed) that must reach every other phone, so they are LWW
here while the server still refuses row deletes. `message_logs` is LWW rather than append-only because the server owns
WhatsApp delivery state (0008): `sent`/`delivered`/`failed` must reach every
phone, a local cancel still wins until pushed, and the server never regresses
a sent row when a phone replays it. The same path brings back an appointment
confirmed from a WhatsApp reply.

Server-minted values flow back through the LWW path: an invoice pushed with
a `DRAFT-` number and a non-draft status comes back with its `INV/2026-27/0001`
number (the server keeps that number on every later replay), and a patient
number the server renumbers replaces the local one.

### Concurrency and idempotence

`pushPending`, `pullSince` and `syncNow` (push then pull) share one FIFO
mutex, so concurrent calls run one after another and never interleave on the
database or the watermarks. Every step is idempotent: a second push sends
nothing, a re-pull of already-applied rows changes nothing.

### Linking a device

The server pins clinic bootstrap to the creating user (`clinics.created_by`,
first `ownerDentist` member only by the creator), so the first push needs a
link step. `RemoteClinicLinker` records the link in `sync_state`
(`linked_clinic_id`, `linked_member_id`, `link_mode`, `linked_at`); the
engine refuses to run (`SyncStatus.error`, "clinic not linked") until the link
names its `clinicId`.

1. **Sign in** (app, Supabase Auth). `listMemberships(userId)` reads the
   user's active `clinic_members` rows.
2. **First device** (no membership, a local clinic exists):
   `pushLocalClinic(localClinicId:, ownerMemberId:, userId:)` upserts the
   clinic (the server fills `created_by`) and the owner member with
   `user_id = userId`, the one insert the bootstrap policy allows, then
   records the link. The outbox then drains normally; its replay of the same
   two rows is harmless.
3. **Second device** (a membership exists, the device holds no clinic and no
   pending writes): `adoptRemoteClinic(membership)` records the remote
   clinic and member ids. The app builds its `ActorContext(clinicId:
   membership.clinicId, actorId: membership.memberId, deviceId: ...)` and
   runs `pullSince(null)` for the full first pull. Adopting with local data
   present throws `StateError`.
4. **Mismatch** (the user belongs to another clinic than the device holds):
   `pushLocalClinic` throws `StateError`; the app must ask the user to keep
   the local clinic and sign in with its account, or wipe and adopt.

### Audit de-duplication

The server audits every upsert a phone sends (`app.audit_row()`, `device_id
= 'server'`, nil actor), so pulling those rows back would give each local
write a second audit event. `audit_events` is flagged
`SyncTable.skipServerAuthored`: the pull adds `device_id=neq.server` and
`actor_id=not.is.null` unless the engine was built with `includeServerAudit:
true`. Locally, `AuditRepository.watchRecent(clinicId, includeServer:
false)` (the default) hides events whose `deviceId` is `server`, so the
audit screen can toggle them.

### Message log provider

`MessageLog.provider` (`MessageProvider.deeplink` | `cloudApi`, stored and
sent as the wire name `deeplink` | `cloud_api`; `smsGateway` mirrors the
server constraint) and `MessageLog.optInReason` are columns since schema v6.
The upgrade backfills both from the legacy `variables._provider` /
`variables._opt_in_reason` stamps (`AppDatabase
.migrateLegacyMessageLogStamps`, idempotent; the stamps stay in `variables`
because the server trigger still reads them into `provider` and, since
0011, `opt_in_reason`) and `MessageLog.fromJson` falls back to the stamps
for rows that carry no field.

### Logging

Logs name tables, row counts, attempt numbers and error classes
(`PostgrestException 500 on patients`), never row contents. `SyncState.error`
carries the same text and is safe to show.

### Pointing the app at a project

Configuration comes from `--dart-define-from-file=env.json` in
`apps/app_mobile` (`SUPABASE_URL`, `SUPABASE_ANON_KEY`; `env.example.json`
is committed, `env.json` is gitignored). Create the project in Mumbai
(`ap-south-1`), copy the project URL and anon key into `env.json`, then run
`flutter run --dart-define-from-file=env.json`. Nothing in this package reads
the environment; the app constructs the `SupabaseClient` and passes it in.

The server must have:

* every migration in `supabase/migrations` applied in order
  (`supabase db push`, or `psql -f` each file) so the tables, the
  `app.touch_updated_at()` / `app.audit_row()` / `app.invoices_assign_number()`
  triggers and the number-minting functions exist;
* RLS enabled with the policies from `0002_rls.sql` and `0006_...sql`
  (membership through `clinic_members.user_id`, append-only tables without
  an UPDATE policy, clinic bootstrap pinned to `created_by`);
* Supabase Auth with the sign-in method the app uses (phone OTP via the
  Send-SMS hook, see `docs/research/03-architecture-and-data.md`);
* no Realtime, no Edge Functions and no Storage are needed for sync.

## Server parity

`supabase/migrations/*.sql` mirrors these tables. `test/schema_parity_test.dart`
parses the migrations and fails when a Drift table has no `create table
public.<name>` (outbox rows would have no target) or a server tenant table has
no Drift table. Deliberate exceptions, each with its reason in the test:
local-only `sync_outbox`, `perio_site_readings` and `sync_state`; server-only
`profiles`, `gst_rates`, `devices` and `clinic_whatsapp_configs`. Column names
follow drift's snake_case of the Dart field (`reminder24hSentAt` ->
`reminder24h_sent_at`); money columns are suffixed `_paise` server-side.
`test/sync/sync_plan_codec_test.dart` checks every synced column by name.

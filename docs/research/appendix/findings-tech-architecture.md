# Findings: tech-architecture

Raw research output from the multi-agent sweep (October 2026). Each finding carries a verification tag:

- `confirmed` (11): passed independent fact-check
- `corrected` (6): fact-checker corrected the claim; text below is the corrected version
- `disputed` (7): two fact-checkers disagreed; treat as uncertain
- `unverified-low-risk` (2): not fact-checked (judged low-risk)

## Summary

Flutter is a sound choice for a dental-only clinic product in late 2026, and the case is stronger than it was two years ago. The current stable is Flutter 3.47 (12 Aug 2026, Dart 3.13); Impeller is now the only renderer on iOS, default on Android API 29+, and default on macOS/Windows/Linux as of 3.47, so a CustomPainter-heavy odontogram and perio chart render through one GPU pipeline on every native target. Web is the weak spot: CanvasKit (Skia) remains the default for `flutter build web`, and the `--wasm` (skwasm) path only runs on Chromium 119+ with JS fallback elsewhere, and cannot run on any iOS browser. React Native + Expo (SDK 57, RN 0.86) is a credible alternative that the founder already knows, but the heavy-canvas requirement cuts against it: production write-ups of react-native-skia report path re-tessellation stalls on Mali GPUs, JS-to-GPU backlog "rubber-banding" on mid-range clinic tablets, and canvas content invisible to TalkBack/VoiceOver unless a parallel accessibility tree is hand-built. Flutter's PDF/printing/signature packages are also more mature and better maintained than their RN equivalents. The honest trade-off is hiring (US LinkedIn shows roughly 6x more RN jobs than Flutter) and the founder's existing Expo/Next.js muscle memory.

For data, the 2026 landscape has consolidated. Isar is dead (original repo archived 18 Aug 2025; `isar` on pub.dev last published 3 years ago; the community fork itself moved again), Realm/Atlas Device Sync reached end-of-life on 30 Sep 2025, and ElectricSQL has no official Flutter client. The maintained options are Drift (2.35.2, 2.48k likes, published days ago, MIT, SQL on SQLite, web via WASM) for relational data and Hive CE (2.20.2, encryption + isolates + WASM) for key-value. For offline-first sync the dominant Flutter pattern is Supabase Postgres + RLS as the system of record with PowerSync replicating per-tenant slices to on-device SQLite via logical replication; writes queue locally and replay through the Supabase client so RLS still gates every write. PowerSync is Free up to 50 peak clients, Pro from $49/month (1,000 peak clients, 30 GB synced), Team $599 (HIPAA/SOC2), with an Open Edition for self-hosting. Supabase has a Mumbai region (ap-south-1), AES-256 at rest, SOC 2 Type 2, HIPAA BAA on Team/Enterprise, Pro at $25 + compute, PITR at $100 per 7 days. Firebase is less attractive for medical records: Firebase Authentication, FCM and Crashlytics are not on Google's HIPAA covered-products list (Firestore, Cloud Storage, Identity Platform, Cloud SQL are), Firestore security rules cannot express joins, and phone OTP is billed per SMS at roughly ₹5-6 in India versus ₹0.18-0.25 via MSG91.

Dental-specific tooling is thin, which is the opportunity and the cost. No pub.dev package implements a real odontogram (surfaces, conditions, treatment states, mixed dentition): `teeth_selector` (7 likes, 250 downloads, 21 months stale) and `dental_teeth_selector` (10 likes, 402 downloads, FDI + Universal) are tooth pickers only. Plan to build the odontogram and six-site perio grid as CustomPainter with your own geometry and hit-testing, keyed on FDI/ISO 3950 with Universal as a display option, and align the data model to the HL7 Dental Data Exchange FHIR R4 IG (v2.0.0-ballot, 7 profiles, Tooth Identification and Oral Cavity Area value sets, SNOMED CT primary with SNODENT translations). India-side compliance is concrete and dated: DPDP Rules notified 13 Nov 2025 (G.S.R. 846(E)), consent-manager rules live 14 Nov 2026, substantive duties (notice, consent, breach reporting, erasure, cross-border negative list) 14 May 2027; ABDM M1/M2/M3 integration is the path to ABHA-linked records and is being mandated for institutions under NMC, with dental clinics not yet explicitly covered. Messaging economics are favourable: Meta's INR rate card is ₹0.115 per utility/authentication message and ₹0.8631 per marketing message (plus 18% GST), 1,000 free service messages per number per month from 1 Oct 2026, with Gupshup adding only $0.001 per message and Interakt/AiSensy charging ₹0.95-1.09 marketing / ₹0.14-0.16 utility inclusive plus ₹1,500-3,800 monthly plans. A reminder-heavy clinic sending ~1,800 utility messages a month costs about ₹210-290 in Meta fees.

Recommended architecture: Flutter 3.47 monorepo (Melos 8.9 on pub workspaces, Dart >= 3.9) with `app_mobile`, `app_desk` (Flutter web/desktop for the front desk, CanvasKit default, optional wasm for Chrome users), and shared `core`, `odontogram`, `pdf_templates`, `sync` packages; Drift + sqlite3 as the local store, PowerSync Pro against Supabase Postgres in ap-south-1 with a shared schema + `clinic_id` + RLS (indexed, `(select auth.jwt())` pattern, `to authenticated`); Supabase Auth with the Send-SMS hook routed to MSG91 for Indian OTPs; Supabase Storage for compressed intraoral photos (flutter_image_compress, keepExif) and raw DICOM/JPEG X-rays (dicom_viewer for in-app viewing); `pdf` + `printing` + `signature` for invoices, prescriptions and consent forms; a small NestJS or Supabase Edge Functions service for WhatsApp Cloud API webhooks, Razorpay/Cashfree payment links and future ABDM M1-M3; Codemagic free tier (500 Mac minutes) initially, GitHub Actions later. Alternatives with reasons: Serverpod 4 (full Dart, SSPL, embedded client SQLite; smaller ecosystem, no managed RLS story), NestJS + Prisma on your own Postgres (founder knows it; you give up Supabase Auth/Storage/RLS tooling and PowerSync's Supabase integration shortcuts), Firebase (fastest offline story but BAA gaps and weak tenant isolation), and Expo + op-sqlite + PowerSync RN SDK (viable if hiring dominates and the odontogram is kept simple).

### 2. `confirmed` · confidence high

Flutter web: `flutter build web` still produces a CanvasKit (JS) build; `--wasm` (dart2wasm + skwasm) requires WasmGC and runs only on Chromium 119+, falls back to JS at runtime, and cannot run on any iOS browser; Firefox and Safari have open bugs blocking Flutter's wasm renderer. Multi-threaded wasm rendering needs COOP/COEP headers. dart:html and package:js code does not compile to wasm.

**Why it matters:** A Flutter-web front-desk app is realistic for clinics on Chrome/Edge desktops (most Indian clinic PCs), but treat wasm as a Chromium-only optimisation and avoid dart:html in shared packages. If the founder wants the receptionist web app to be broadly browser-portable with SEO-free admin UX, Flutter web (CanvasKit) is acceptable; if a public patient-facing site is needed, keep Next.js for that.

### 3. `unverified-low-risk` · confidence high

Desktop/multi-window and large screens: Flutter 3.47 ships a multi-window API (platform handles, Win32 and Linux popup windows, sized-to-content dialog windows) and Impeller-by-default on desktop; Flutter's large-screen guidance says do not lock orientation, use MediaQuery window size (not device type) for column counts, and swap BottomNavigationBar for NavigationRail. Android 16 (targetSdk 36) ignores orientation/resizability/aspect-ratio restrictions on sw>=600dp displays, with the opt-out removed at API 37; Flutter lists this as a breaking change in 3.44.

**Why it matters:** Dentists chart on 10-13 inch tablets in landscape and receptionists use desktops; the app must be built adaptive from day one (NavigationRail + two-pane chart/notes layout) because Play will force resizability on tablets and surfaces per-device ratings for large-screen support.

### 4. `disputed` · confidence medium

Flutter vs React Native/Expo for a dental clinic app (as of 11 Oct 2026): Expo SDK 57 shipped 30 Jun 2026 on React Native 0.86 / React 19.2 (correct), and Expo SDK 58 beta opened 15 Sep 2026 bundling the React Native 0.88 release candidate (not 0.87), with stable SDK 58 to follow RN 0.88 stable. ### 6. `confirmed` · confidence high

Supabase + PowerSync is the turnkey offline-first pattern for Flutter: PowerSync reads Postgres via logical replication (dedicated replication role with BYPASSRLS, a `powersync` publication listing specific tables), Sync Streams define per-user/per-tenant slices (e.g. rows where clinic_id matches a JWT claim) into on-device SQLite, writes queue locally and replay through the Supabase client so RLS applies to every write, and PowerSync validates Supabase JWTs via JWKS. Pricing: Free ($0; 2 GB synced, 500 MB hosted, 50 peak clients), Pro from $49 (30 GB synced, 10 GB hosted, 1,000 peak clients; overages $1/GB synced, $1/GB hosted, $30 per extra 1,000 peak clients, $25 per extra instance), Team from $599 (HIPAA, SOC 2), Open Edition free self-hosted. PowerSync's own example: 50k installs / 5k DAU costs ~$51/month on Pro.

**Why it matters:** A dentist in Arunachal Pradesh or a tier-3 town cannot depend on connectivity during a procedure; this stack gives instant local reads/writes with server-side tenant isolation, and the cost at 100-1,000 clinics is tens of dollars a month. Design Sync Streams to mirror RLS exactly and partition by clinic_id from day one.

### 8. `confirmed` · confidence high

Multi-tenant RLS pattern and performance: Supabase's official guidance is to index every column a policy filters on (a composite PK only indexes its first column), wrap auth functions as `(select auth.uid())` / `(select auth.jwt())` so Postgres evaluates them once per statement (initPlan), always scope policies `to authenticated`, and move membership lookups into `security definer` functions with `search_path = ''`.
